# 齐论AI人才管理系统｜完整产品与工程需求

版本：v1.0  
编制日期：2026-09-17  
文档性质：产品需求、工程约束与验收基线；不是已经开发、上线或验证成功的系统。  
使用对象：Codex、产品负责人、前后端工程师、测试人员、招聘负责人。

## 0. 项目定义与不可混淆的前提

### 0.1 产品定位

建设「齐论AI人才管理系统」，以招聘与人才档案为主线，提供独立的电脑管理后台和手机H5测评入口。它不是只有一个MBTI答题页面，也不是第一版就包含薪酬、考勤、社保、工资核算的全量人事ERP。

第一版范围：岗位管理及优化、招聘渠道接入、简历导入与筛选、云端人才库、测评管理、专属H5邀请、测评报告、面试提纲、面试录音/文稿管理、综合评估、员工档案、AI配置、权限与审计。

核心链路：

```text
岗位创建/同步 → 岗位标准确认 → 合法授权的简历接入
→ 解析去重 → 岗位证据初筛 → 人工查看
→ 选择「岗位 + 候选人 + 简历版本 + 测评版本」生成邀请
→ H5确认与答题 → 固定计分/授权结果导入 → 分层报告
→ 岗位证据面试提纲 → 面试记录/录音转写 → 证据复核
→ 人工决定下一步 → 未邀约储备/录用/员工发展档案
```

员工链路：选择员工 → 选择发展目的与测评包 → 生成个人链接 → H5答题 → 员工报告 → 发展面谈。不强制绑定招聘岗位。

### 0.2 需求、原站证据与新增设计分开

本文件中的功能、数据结构、默认设置和新系统验收要求，除明确注明来源外，均为本项目设计，不声称来自高禾原系统。

原站材料索引见 `docs/02_测评证据与兼容边界.md`，原件在 `evidence/`。五份材料是分析文稿，不等于完整题库、后台源码、真实报告数据集或文稿内列举的JS/JSON原件。文稿中的 `/mnt/d/...` 是既有环境路径；Codex必须先检查本机是否存在，不能按“文稿列出了路径”认定文件已取得。

本轮未检索到此前其他题目和结果样本的可读原件；不得把历史助手的概括、主观评分或当前简历分析意见当成测评计分键、标注真值或黄金测试集。

### 0.3 对「100%一致」的处理

用户期望原题、选项、计分和结果一致，应建立可验证的兼容目标，不得以近似题库或大模型生成结果冒充原版。

当前材料明确：完整题项计分键、标准化/常模、岗位标杆聚合、正式分项匹配及综合匹配公式未取得。已知的选项编码不等于维度分；前端辅助公式不等于后台实际算法。[E1 §一、七；E2 §六]

提供三种独立运行方式：

| 方式 | 可做什么 | 发布条件 |
|---|---|---|
| 授权原引擎接入 | 由获准使用的服务生成结果，本系统收取授权结果 | 有真实可用的接口/跳转回传方式、使用授权与完成样本 |
| 授权规则兼容引擎 | 本系统执行原题库、计分配置与模板 | 取得可用的完整规则包，并完成逐项回归；不以几个样本宣称全域等价 |
| 外部报告导入 | 导入受测者允许使用的真实报告，支持人工校对后用于后续流程 | 清楚标识「外部导入」，不得声称在本系统重新计分 |

若上述计分条件尚未具备：先交付可用的岗位、人才库、面试和报告导入功能，以及H5/规则引擎框架。演示题只能位于演示环境，明确标识「原创演示题，不是正式测评，不产生招聘判断」。正式测评发布按钮应显示具体缺项并阻止发布。

### 0.4 三条产品约束

第一，人才库不是无限期抓取仓库。未邀约者可以依法进入储备库，但必须有明确用途、适当处理依据、保留期限和删除/退出机制。公开可见不等于可无限制收集、画像、转交和永久保存。[R1]

第二，自动筛选是辅助整理和人工审阅排序，不是无人复核的自动淘汰。岗位技能、项目行为、作品与可核实经历作为招聘判断依据；MBTI和自述性格单独展示，不作为录用评分、岗位排除、自动调岗或“文化匹配度”。正式MBTI提供方明确其不适用于招聘甄选。[R2]

第三，招聘平台接入需要平台允许的接入方式和数据处理权限。用户在平台登录、网页能看见、软件能操作，不能单独证明获准批量自动获取。本方案未核实BOSS为该账号提供授权简历API或允许无人值守插件访问，相关能力默认待验证。[R3]

## 1. 用户角色、访问边界与组织

### 1.1 角色

| 角色 | 默认能力 | 默认不可做 |
|---|---|---|
| 系统管理员 | 组织、账户、模型供应商、系统参数、运行监控 | 仅凭运维身份读取全部人格报告与招聘私密记录 |
| 老板/人才负责人 | 已授权组织的岗位、招聘进度、人才审阅、人工决策 | 跨独立主体无授权获取人才数据 |
| HR | 所属岗位与候选人维护、邀请、面试安排、档案管理 | 读取完整模型密钥、修改已发布计分规则 |
| 用人负责人 | 授权岗位的候选人、面试题与评价 | 浏览其他部门的全部人才库 |
| 面试官 | 被分配的面试包、提纲、本人评价 | 默认导出所有联系方式或查看其他面试官未提交意见 |
| 员工 | 通过专属H5完成测评、查看本人已发布发展报告 | 登录招聘管理后台、查看同事报告 |
| 候选人 | 专属邀请内的身份确认、答题和本人报告 | 查看岗位内部评分标准、面试官备注、他人信息 |

角色可以组合；权限采用角色权限加对象授权，而不是仅靠前端隐藏按钮。联系方式查看、数据导出、人格报告查看、规则发布、人工决定、AI配置、跨组织分享分别授权。

### 1.2 组织与统一登录

第一版支持公司、部门、招聘岗位负责人；为未来兄弟公司预留独立租户。默认不同公司数据隔离，不能因为共同品牌或共同投资就自动共享候选人资料。

若现有统一登录可用，接入已有OIDC身份服务，使用 `(issuer, sub)` 映射员工身份，不复制各站密码库。统一登录只解决“是谁”，本系统独立判断“可以看什么”。若身份服务未就绪，先提供内部管理员开户方式，不开放后台自助注册。

每次访问、后台任务、搜索、向量检索、导出、对象存储下载均必须携带从可信身份上下文确定的租户和权限范围。独立公司的共享需要单独授权和用途记录，分享不等于授予对源档案的全部访问权。

### 2.2 视觉和交互基线

品牌名统一「齐论AI」，不得使用语音误写。采用企业管理工具风格：清晰导航、稳定表格、留白、可靠的信息层次，不做满屏炫光或大面积低对比渐变。

暂定UI建议色：主色 `#155EEF`，侧栏 `#0B1020`，页面背景 `#F6F8FC`，卡片 `#FFFFFF`，主文字 `#101828`。这些是本方案建议，不声称是此前海报精确取样的官方VI色值。全部放入设计变量，后续可替换。

桌面优先1440宽，1280宽可完整操作；侧栏约224，顶部约64，正文14～16，统一8点间距体系。H5覆盖360～430宽，主要按钮高度至少44，正文至少16，尊重减少动画偏好，支持键盘与屏幕阅读器。状态不能只靠颜色区分。

所有列表有搜索、组合筛选、保存视图、分页、列设置、权限内批量操作。全部页面处理加载、空数据、无权限、服务故障、部分成功、配置未完成状态。演示数据与真实数据视觉上明显分离。

## 3. 岗位中心与岗位优化

### 3.1 岗位数据

每个内部岗位独立于招聘渠道。必填：岗位名称、所属组织、负责人、办公地点/工作方式、主要任务、当前状态；招聘人数、薪资、经验、学历、到岗要求等按业务填写，不擅自补事实。

岗位结构至少包含：岗位目标、核心任务、预期交付物、必要技能、可培养项、加分经历、工作条件、协作对象、招聘流程、面试评价维度、作品/实操要求、试用期任务建议、对外JD、内部说明。

学历或经历门槛须能说明与工作相关的理由。不得把年龄、性别、婚育、民族、宗教、健康状况、照片外貌、MBTI类型设为默认筛选维度；不以学校声望代替岗位能力。

必要条件单独维护为结构化规则：字段、比较方式、期望值、理由、是否需要核实、缺失处理。简历未写不自动等于不符合。若岗位要求本身不清楚，状态为「岗位标准待确认」，不启动无人审阅式评分。

### 3.2 岗位版本

每次采纳修改新建 `job_version`，保存原稿、建议稿、差异、确认人和时间。已生成的邀请、筛选报告、面试提纲绑定当时岗位版本，不被后来的岗位编辑静默改变。

岗位主要状态：草稿、待确认、招聘中、暂停、关闭、归档。关闭不删除候选人历史，停止新的自动筛选任务；已发出测评是否继续由HR明确选择，不能擅自使作答失效。

### 3.3 AI岗位优化

输入可以是简短描述、已有JD、合法上传文档或粘贴文本；语音描述可先转写再人工确认。

输出分三层：对外可发布JD、内部岗位成功标准、建议面试与实操题。每条新增内容标为「根据原文整理」「建议补充」「需要确认」，不得把建议薪酬、绩效、公司福利、发展承诺写成已确认事实。

例：「想找能帮我推进事情的助理」应转化成待确认的任务类型、跟进机制、会议纪要交付、风险提前报告、跨部门协调边界，不生成“必须外向”“某人格优先”等筛选要求。

操作：生成、停止、局部重写、修改语气、确认必要条件、逐项采纳、保存新版本、复制渠道适配稿。AI优化不能直接替老板发布岗位或修改外部平台内容。

## 4. 岗位渠道同步

### 4.1 内外映射

一个内部岗位可以关联多个渠道发布记录：BOSS、其他招聘平台、公司自有页面、人工渠道。记录渠道账号、外部职位ID、外部原文、状态、地址、最近读取时间、内部映射、同步版本和差异。

第一次导入外部岗位，HR确认映射到已有岗位或新建岗位。禁止仅凭相同标题自动合并，也禁止将不同用工主体混为一岗。

### 4.2 同步优先级

优先使用平台提供并获授权的接口/导出方式；其次是平台允许的数据导出后导入；浏览器辅助与自动化仅在明确允许范围内启用。没有可用通道时保留粘贴JD和手动登记渠道链接，显示「人工维护」，不显示假同步成功。

外部更新写入渠道快照并生成差异，HR确认后再更新内部岗位。内部修改生成待发布稿，只有已验证写接口且人工批准时才推送外部；否则提供复制文案。同步读取失败不能将岗位自动标为关闭或删除。

## 5. 招聘渠道、浏览器插件与自动获取

### 5.1 渠道能力矩阵

每个渠道实例配置以下能力，默认关闭未知项：

```text
read_job_postings / read_candidate_profiles / import_resume_files
incremental_sync / background_fetch / export_allowed
message_send / invite_send / job_write
```

每项记录：验证状态、平台授权依据、数据范围、账号、有效期、配额、最近验证时间、适配器版本。业务任务必须检查能力和授权，不以“管理员勾选同意”替代真实平台许可。

BOSS等未验证接入第一版交付适配接口、配置页和人工导入；不得宣称「BOSS已全自动打通」。取得真实许可后再进行自有账号联调。插件是一种实现形态，不是规避平台规则的途径。

### 5.2 浏览器辅助形态

在允许的站点和页面范围内，可采用Chrome/Edge兼容扩展。第一次由招聘人员人工登录原平台，本系统不索取平台密码，不把平台Cookie上传云端，也不共用账号登录态。

扩展只请求已批准站点的最小权限。默认不请求全站访问、全浏览记录、cookies、debugger权限；新增权限必须说明理由。使用本系统短期、设备绑定、最小权限令牌与云端通信，支持远程吊销。

界面显示：当前公司、岗位、采集模式、授权范围、今日处理数、正在处理项、暂停按钮、异常原因。操作前可预览拟同步字段。

电脑关闭或扩展离线时，状态为「等待设备在线」，不能假装还在云端读取平台。扩展后台可能休眠，任务进度必须持久化并由事件恢复，不能依赖一个永久运行的内存循环。[R4]

### 5.3 自动化允许范围

已许可的后台获取任务需具备：账号锁、速率额度、断点续传、重试上限、异常停止、审计日志和人工接管。

验证码、账号验证、登录失效、访问被拒、额度耗尽、页面结构异常时立即暂停相应通道，保留已处理结果。不绕过验证码、不换IP/账号躲限、不读取隐藏联系方式、不调用猜测的未授权接口、不自动购买解锁、不自动发消息邀约。

### 5.4 「每天500份」的定义

`daily_screening_target = 500`是用户配置的处理目标，不是平台已允许的读取配额，也不是保证每日获取500份新简历。

分别计数：已发现、允许接入、唯一候选人、新简历版本、成功解析、已完成当前岗位评估、需人工查看、重复跳过、等待授权、失败、已人工联系。

相同候选人同一简历版本同一岗位标准不重复计为新筛选。多岗位匹配另计任务数和费用。平台只允许读取200份时，不为凑500重复刷取；已导入的合法资料可继续在云端批量处理。

## 6. 自动筛选任务

### 6.1 创建任务

字段：组织、岗位版本、候选人来源、授权渠道、范围/增量起点、执行方式、时区、每日目标、停止条件、预算、负责人、规则版本、AI模型配置。

启动前预检查：岗位已确认、授权有效、数据允许用途、渠道能力可用、模型可用、预算足够、无重复运行。缺一显示具体原因，不默默降级为全网抓取。

### 6.2 流水线

```text
接入/上传 → 文件安全检查 → 提取可读内容 → 来源与处理依据校验
→ 候选人关联/待去重 → 字段抽取与原文定位
→ 去身份化的岗位证据比较 → 输出未知项和待问问题
→ 写入当前岗位评估快照 → 人工审阅队列 → 合规储备/招聘推进
```

低成本解析、规则检查先执行；内容难以解析再进入OCR/视觉解析；重要或有冲突的资料才进行较完整的AI分析。资料缺失不生成“能力不足”的结论。

### 6.3 AI初筛输出

输出不是“这个人值82分”，而是每项要求对应：明确有材料支持、部分支持、需核实、明确条件冲突，以及证据来源、是否本人自述、下一步核验建议。

审阅队列可按用户确认的岗位相关规则排列为：优先人工查看、需要补充信息、需要核对条件、其他岗位值得查看。不得据MBTI或心理标签排序。所有队列均可回看，最终不邀约/不通过由有权限的人确认并记录理由。

可选的数值只能叫「岗位证据覆盖率」或「规则符合度」，必须说明计算定义和缺失比例，不叫“录用成功率”“真实能力分”。默认不用综合人格分合并招聘排序。

## 7. 简历导入、解析与证据

### 7.1 输入

支持PDF、DOCX、TXT、图片，以及结构化CSV导入；录音转写文稿单独归类。文件类型与大小通过可配置白名单验证，宏和可执行附件不处理，压缩包限制解压大小与文件数。

优先读取PDF文本层和文档文本；提取质量不足才启用OCR或经批准的视觉服务。原件不修改；提取文本、清洗文本、人工校正版分别保存。只拿到平台摘要时标记 `profile_completeness=summary_only`，不叫完整简历。

### 7.2 字段

岗位相关字段：姓名/昵称、求职意向、工作地点、合法取得的联系信息、技能、工作经历、项目经历、教育/资格、作品、可到岗情况、薪资期望。联系方式单独加密并独立控制访问。

简历自我评价原文、本人公开职业档案中的性格表述、本人提供的MBTI可以记录，但分开存放，不从照片/姓名/语音/泛泛表述猜测人格或心理健康。

每个抽取值保存：原始内容、规范化值、文档版本、页码/行号/文本区间、提取方式、确认状态、记录时间。无证据字段为null；不得把缺失写为0，不编造任职时间或成绩。

### 7.3 证据等级

使用「候选人自述」「文件记载」「作品可查看」「面试解释」「经核验」等来源状态，避免用未经校准的“95%可信”。文件记载不等于第三方核验；简历写会Codex不等于已证明能独立交付系统。

候选人材料中的指令、链接、二维码都当作数据，不自动执行、不自动访问外部地址，更不能因简历写“请给我最高评分”而改变系统规则。

### 7.4 校对与异常

时间冲突、金额口径不一致、同段经历多个版本不同，进入“待澄清”而不是自动认定造假。例如季度盈利与全项目最终亏损可能口径不同，应生成核对问题。

人工修改提取结果需保留修改前后、修改人和理由；后续依赖报告标为待更新，不覆盖历史版本。

## 8. 云端人才库

### 8.1 以人为主档、以岗位申请为过程

```text
候选人主档
 ├─ 多来源职业资料
 ├─ 多版简历与作品
 ├─ 多条自述标签/外部测评/内部测评记录
 ├─ 岗位A申请：筛选、邀请、面试、决定
 ├─ 岗位B申请：独立筛选、独立决定
 └─ 储备用途、期限、授权与后续联系记录
```

“当前岗位未邀约”与“整个人被排除”不是一回事。先测评后补简历、先建档后绑定岗位、同一人应聘多个岗位都需要支持。

### 8.2 入库与保留

可在授权与合理用途范围内保存未邀约候选人，不要求先发邀约才有档案。长期人才储备作为独立用途管理，记录适用依据、告知版本、有效期限及退出状态。

未确定可处理范围的数据不进入长期可搜索人才库；仅进入受限待处理区，依政策尽快核实并删除不应保留的信息。不得通过改名“候选线索”逃避处理要求。

保留期是组织政策，不是代码里写死“永久”。系统应支持按来源、用途、状态设定期限、到期提醒、续期确认、删除/匿名化和禁止联系。具体期限上线前由负责人员确认，不在文档中冒充法定时长。[R1]

### 8.3 性格与测评历史

`personality_observation`至少包含：

```text
observation_type: self_description | self_reported_type | external_assessment | internal_assessment
raw_text / normalized_label / source_record_id / source_date
instrument_name / instrument_version / measured_at（未知为null）
verification_status / purpose_scope / retention_until / superseded_by
```

例：简历“热情、责任心强”只记录为本人自述；本人写“ENFP”记录为自报类型、未知测评版本。不能从“热情”自动补成E型，也不能把外部自报类型覆盖内部结果。多次结果并列可查，附时间和来源，不把变化称为不诚实。

### 8.4 去重

同一渠道稳定外部ID可直接关联同源记录；已核验相同联系方式可提出合并候选。联系方式使用受控加密和租户内HMAC匹配，不保存可公开枚举的普通散列索引。

姓名、头像、学校相同只作为待人工核实线索。合并必须可回退、保留来源；不跨独立租户自动合并。旧来源错误和候选人更正要能同时追踪。

### 8.5 搜索与再匹配

支持技能、项目类型、行业经验、地点/工作方式、期望薪资、到岗、作品状态、来源、更新时间等筛选，以及自然语言查找岗位相关经历。

自然语言例：“找有AI工具实作、能拿出作品、有项目推进经验、愿意在杭州工作的人”。不把“年轻”“外向”“某MBTI”等作为默认招聘筛选。

新岗位可对允许该用途且未过期的储备资料重新匹配；显示资料多久未更新、求职意向是否需要再确认、建议人工联系。不自动发骚扰式通知，不因新岗位出现而擅自延长数据保留期限。

## 9. 岗位评价与性格信息隔离

### 9.1 招聘评价输入

岗位必要任务、候选人提供的相关经历、作品/实操、面试中能核对的具体回答。模型输入默认移除照片、完整联系方式、精确年龄、婚育及其他与岗位无关的信息。

MBTI、人格偏好、所谓情绪稳定性、自报兴趣不能作为工作能力代理变量。报告可以在单独授权的发展/沟通部分呈现自述偏好，但不进入招聘规则、排序索引、人工打分模板或替代岗位推荐。

### 9.2 证据矩阵

每项岗位标准有编号、定义、可接受证据、核验问题和权重（可选）。评分状态与证据可靠性分开：某项有自述材料支持，不等于已验证真实能力。

可选覆盖率的项目自定义公式：

```text
证据覆盖率 = 已有可定位材料的岗位标准权重之和 / 全部已确认岗位标准权重之和
```

“有证据”包括支持和冲突，不表示候选人优秀程度。没有有效标准或分母为0时返回null。该公式是齐论本系统定义，与高禾计分没有关系。

若启用其他规则分值，必须配置可解释的值域、缺失策略和用途，保存规则版本；不得自动把未知项补中位数以制造完整分数。

### 9.3 人工复核

HR能修改AI的结构化判断并填写依据。AI重新运行不得覆盖人工决定。进入下一轮、暂缓、不邀约、发录用信息等有不同确认动作；批量操作也要列出对象与理由预览。

招聘偏好改进从经审核的岗位标准和真实可核验交付出发，不让系统自动学习老板对年龄、性别、人格类型、长相或“顺眼程度”的偏好。

## 10. 测评模块与原系统兼容

### 10.1 七类模块预留

依据用户材料，预留以下报告/模块容器，但未取得规则的模块不能生成正式分数。[E5 §二]

| 模块 | 文稿支持的结构 | 工程实现约束 |
|---|---|---|
| 元五人格 | 情绪性、宜人性、外倾性、尽责性、创新性 | 不冒称某正式标准量表；五因素与四维类型分开 |
| 职业风格 | E/I、S/N、T/F、J/P，16型结构 | 未确认正式MBTI量表及计分；仅用于适当的发展用途 |
| 职业角色 | 8类角色 | 具体名称与题项计分待材料，不自造冒原版 |
| 职业能力 | 28项，社交、思维、自我态度、执行等汇总 | 自陈结果不当成实操验证能力 |
| 职业动机 | 财富、健康、享受、工作、创新、情感、荣誉、权力 | 已知部分报告衍生计算，基础分来源未知 |
| 职业价值观 | 8类；64词分组选择后排序的流程 | 词库、排名权重和维度映射不齐时不可正式发布 |
| 职业优势 | 执行、思维、关系、影响四类才干 | 不根据分类名称推断原版盖洛普题库或计分 |

### 10.2 题库管理

题库、选项、模块、计分规则、解释模板、常模配置各自版本化，并共同组成一个不可变的 `assessment_package_version`。

题目字段：本系统题ID、来源题ID、题型、题干、A/B陈述、选项文本与编码、模块、顺序/分组、时间规则、可用语言、资源引用、内容授权、状态。计分映射字段另存服务端，不随题目API发给H5。

题型至少支持：A/B双陈述五档、单陈述符合度五档、词语分组选择、二次选择、排序。开放题可作为岗位补充问答，必须标明不属于原测评、不并入原量表得分。

### 10.3 已知答案编码

A/B五档按原页面编码1～5；单陈述从“完全不符”到“完全符合”的编码是5、4、3、2、1。以上是提交编码，不是维度计分。[E2 §二]

价值观流程：64词分4组，每组选5得到20，再选10并排序，提交排名1～10。未知每个排名贡献多少分。不要默认线性倒序计分。[E2 §二.4]

64题只是当前职业定位配置值；文稿只报告真实取得3道不同题目。不能硬编码287作为完整题库总题数，不把模块说明中的28或153当成已到手题库。

### 10.4 原站行为与新系统可靠性

材料记录了原站超时自动补中立、连续跳页删除答卷等前端行为，以及可能的排序DOM不同步情况。[E2 §二.4—5]

兼容分析应保留这些观察，但本系统不得默认自动造答案、删除正式答卷或让隐藏DOM顺序覆盖用户可见排序。新实现保存真实缺答状态、提供暂停/继续，质量异常提示人工复核。若为了授权兼容确需特殊行为，应通过明确、版本化的兼容配置和受测告知启用，并列出与安全默认的差异。

不能把“答题快”“中立多”直接标为测谎、品行差、工作能力差或自动不录用。

## 11. 固定计分引擎与结果状态

### 11.1 计分不交给大模型自由发挥

```text
score(package_version, answer_snapshot)
→ raw_dimensions / transformed_dimensions / quality_flags
→ score_trace / engine_version / status
```

授权规则已完整时，这一过程是确定性服务端计算，不需要LLM Token。大模型只消费已算好的结构化结果做可选解释，不能改变基础分、人格类型或已确认规则。

### 11.2 规则包发布校验

发布前检查：题目完整、选项唯一、题型合法、维度定义完整、每个可选答案的计分配置存在、反向/权重明确、标准化配置及来源明确、缺答和并列规则明确、解释模板齐备、内容使用条件明确、回归样本通过。

计分配置可以使用受限JSON规则与白名单运算，不允许管理员上传任意JS/Python后在业务进程执行。复杂的已授权算法通过审核过的引擎实现接入，配置只选择版本。

未知规则不能填0、统一权重或常见心理学公式；`blocked_missing_scoring_rules`是正常可解释状态，不是需要AI自动修复的数据缺陷。

### 11.3 可复现性

保存答案快照、题目/选项版本、计分键版本、引擎版本、常模版本、解释模板版本、报告生成时间及输入哈希。重新生成文字解释不改变原分数；换规则需要新计分记录，并标明为什么重算。

服务器只接受题目ID和合法答案，拒绝客户端上传“最终得分”。限制已提交答卷修改；更正产生新版本，不悄悄改旧记录。

### 11.4 状态区分

```text
答卷：not_started → in_progress → submitted
计分：not_requested → queued → scoring → completed / blocked / failed
解释：not_requested → queued → generating → completed / failed
报告：draft → pending_review → published → superseded / revoked
```

“答题完成”不等于“计分完成”；“计分完成”不等于“AI解释完成”。任一阶段故障都不丢失已提交答卷。报告计分字段缺失时不能伪造完整图表。

### 11.5 原站公式隔离

PC人才报告的动机W/L除数为25/15；手机高级报告为5/3，且输入字段不同。它们必须使用不同适配器，不能假定倍率后合并。[E5 §四.B；E1 §四]

前端 `getSingleMatch` 的85分辅助函数在当前展示调用点未被使用，禁止把它接成本系统正式人岗匹配总分。详细公式及证据边界见专门证据文档。[E2 §四—五]

## 12. 专属邀请与H5答题

### 12.1 生成邀请

主要入口为岗位申请页、人才详情页、员工档案页。HR选择：用途（招聘补充/员工发展）、人员、岗位申请（员工发展可空）、简历版本、测评包版本、有效期、报告可见范围、通知方式。

生成前核对摘要：邀请谁、基于哪个岗位和简历、用哪个测评版本、预计耗时（来自实际配置）、可见哪些报告。明确区分基于岗位的补充问答与独立标准化量表；不能为了岗位A改写同一量表题目而仍称原版测评。

创建后提供复制链接、二维码和可编辑邀请文案。复制不等于已发送；系统只有实际发送回执或人工标记后才记录发送。

一人一个邀请，一个邀请只允许创建一个正式答题会话。多人邀请逐人生成，不共享同一可回看报告的链接。

### 12.2 绑定与版本

邀请持有以下关联：租户、候选人或员工、岗位申请、岗位版本、简历版本、测评版本、创建人、有效期、用途与告知版本。

受测者不能修改绑定的内部ID。发现被邀请人不符时可停止并联系HR，不能用另一人的姓名继续提交。已有资料不足时可让本人补充必要信息，但不得按姓名自动合并旧人档。

重测新建邀请和答题记录，旧报告保留历史。复用既有测评要检查版本兼容、时间、用途和授权，由HR确认，不能复制旧答卷冒充新测评。

### 12.3 无需后台账号，但有访问控制

URL使用高熵随机Token，不包含姓名、电话、候选人ID或管理员会话。数据库只存其摘要，浏览器在显式确认后交换为仅限本次测评的短期会话。

链接GET只显示最小化说明，不消费一次性Token，不自动开始计时，不返回历史简历或完整报告，以免微信预览/安全扫描抢先激活。POST领取会话才改变状态。短期Cookie使用HttpOnly、Secure及适当SameSite策略；完整Token从日志、错误、统计、Referrer中移除。

同一设备允许续答；换设备需要重新验证邀请或联系HR。链接可撤销、延长或重新发放。对于个人结果回看，采用经验证的联系方式验证码或另外的访问凭证；仅凭持有转发链接的模式不得标成已核实本人身份。

### 12.4 H5页面顺序

| 页面 | 内容与动作 |
|---|---|
| 邀请欢迎 | 齐论AI品牌、邀请单位、用途、题型/时间说明、支持方式 |
| 身份确认 | 最小化身份提示；确认本人；必要时验证已有联系渠道 |
| 告知与选择 | 测评用途、可见人员、AI处理、保留、权利入口；储备人才用途单独选择 |
| 作答说明 | 不是知识考试时说明无标准对错；退出/暂停规则；替代评估入口 |
| 模块导航 | 根据实际发布包计算题量和完成度，不使用假287题常量 |
| 正式答题 | 大按钮、进度、自动保存、保存状态、弱网处理、返回限制说明 |
| 提交确认 | 展示未答数量；允许补答或按规则提交缺答，不自动补中立 |
| 完成反馈 | 区分已提交、计分中、报告处理中、待人工发布 |
| 本人报告 | 已获授权可见的分模块结果、来源版本、适用限制、联系与更正入口 |

### 12.5 保存与并发

每次答案变化附带 `client_event_id`、单调递增序号、`expected_revision`，后端按答题会话与事件ID幂等保存；过期序号不能覆盖较新答案。网络失败显示“尚未同步”，本机仅临时保存必要答题草稿，完成或退出后清除，不缓存原始简历与完整内部报告。

提交使用幂等键和事务，确保多点几次只产生一份提交快照和一次计分任务。两个设备同时作答需冲突提示，不静默合并不一致答案。

使用服务器认可的时间策略记录耗时；暂停、断网、切后台与辅助需求分别说明。不可把网络差、设备慢或无障碍调整当成不诚实证据。

### 12.6 手机兼容

微信内置浏览器、iOS Safari、Android Chrome进行真机或等效测试。第一版不依赖微信OAuth即可打开常规HTTPS页面；微信签名分享等专有能力未配置时提供普通复制链接/二维码。不能声称自有站已具备未申请的微信能力。

## 13. 报告体系

### 13.1 三类报告

受测者报告：仅本人获准查看的测评结果与发展说明，不包含招聘内部排序、面试官私密笔记、其他候选人信息或模型密钥。

内部测评报告：授权HR/发展负责人可见，含来源、版本、分模块结果、质量提示与使用限制。未知维度显示“未取得/未完成”，不绘制为0。

岗位综合评估：岗位任务与候选人证据矩阵、面试核验、待补实操、人工下一步。性格偏好可作为独立的发展附件，不混入录用总分或作为排除理由。

### 13.2 模板和AI解读

基础报告由确定性数据加审核过的模板生成；可选AI解读作为独立章节，标记所用数据范围、生成时间和待验证推测。模型故障时基础报告仍可用。

文案不能写“你一定不适合做管理”“这种类型无法销售”等人格定论。能力模块若源自自评，写明自评性质，不能改写成经工作验证的能力结论。报告解释中的结果数值只能引用服务端已计算字段。

### 13.3 导入与导出

外部报告导入需指定本人、来源、测评时间、版本（未知允许空）、使用范围；自动解析后由HR确认关键数字。没有真实结构化结果只保存文档，不臆造缺失分数。

允许导出PDF和授权的数据表；导出前预览范围、确认用途、记录审计。文件使用短期签名链接、私有存储和权限校验，受测者报告与内部报告采用不同生成器/字段白名单。

报告二维码不能默认永久公开；撤销后重新访问不返回报告。已下载副本无法技术上保证收回，管理界面需明确此边界。

## 14. 面试提纲生成

### 14.1 输入快照

输入当前岗位版本、候选人相关简历、作品、前次面试内容和已发现的证据缺口。可读到自述偏好时只形成中立的沟通确认，不以类型决定问题难度、评分或是否进入面试。

默认输出8～12道主问题供HR筛选，可配置数量。岗位必须验证的问题优先，不能因为某人已写得漂亮就少问核心能力题。

### 14.2 问题卡结构

每题包含：问题编号、岗位标准编号、为什么问、来源定位、主问题、追问、可验证的回答要点、需要的作品/数据、预计时间、已问/未问/跳过、面试官备注。

强制区分事实核验与探索问题。不能先写“该人执行力弱”，再设计诱导对方承认的问法；应写“现有材料缺少任务跟进记录，需要核验”。

### 14.3 示例问题（本项目原创）

1. 选择一个你亲自推进的完整项目，说明目标、你负责的部分、每个关键动作、最后交付，以及哪些部分由其他人完成。
2. 请展示一个你自己用AI工具完成的作品；说明怎样验证结果、遇到错误如何定位、哪些地方需要他人帮助。
3. 多件任务同时到来时，你如何确认先后次序？请展示或还原一份实际任务清单，不要求凭记忆说出久远日期。
4. 跨部门出现阻塞时，你和哪些人确认了什么信息、谁承担下一步、如何判断问题真正解决？
5. 简历中的项目阶段盈利与面试中提到的最终亏损分别是什么口径？哪些成本和时间段没有包含在前者？
6. 给一个与岗位实际工作相似的小任务，约定时间和验收标准，观察真实交付，不把无偿完成商业项目当成面试要求。

示例仅展示题型；系统实际生成必须绑定当前岗位和候选材料，不把本次某位候选人的旧判断直接套到别人身上。

## 15. 面试工作台、录音与转写

### 15.1 第一版操作

选择候选人、岗位和面试轮次 → 打开提纲 → 手动记回答/标记已问 → 上传已有TXT/DOCX转写或音频 → 确认说话人 → 核对关键事实 → 生成面试证据摘要。

录音前告知并取得适当同意，记录录音用途与保留范围。第一版优先支持上传既有音频和文稿；浏览器现场录音作为可选能力，依赖设备权限和实际支持验证。不暗中后台录音。

### 15.2 转写流水线

文件校验、分片、音频转写、说话人分段、时间戳、原稿保存、人工校正、版本冻结、证据抽取。长音频任务异步进行，显示每个阶段和错误；不能一段丢失却显示全部完成。

至少支持常见音频格式，实际转码能力以部署组件验证为准。音频价格可能按时长计，不与文本Token费用混成一个数。分片重叠需要去重，保留原始时间轴。

### 15.3 面试证据抽取

每条证据定位到“谁在什么时间说了什么”。面试官提出的示例、总结或猜测不能直接当成候选人自主陈述。对方仅回答“对”，需保留问答上下文，不能扩写成丰富经营细节。

候选人提供具体动作、范围、交付、数据、责任边界，分别记录。缺少细节表述为“本次材料未说明”，不能仅凭谈吐认定撒谎、低智商、人格缺陷或心理疾病。不分析口音、声音特点、外貌推断就业能力。

### 15.4 实时补问

第一版提供“根据已记录内容生成下一问”：面试官主动点击，以已确认笔记或已转写片段为输入，后台异步给3条以内建议，不能打断面试自动发言。

完整实时音频、流式转写与自动刷新追问列为后续增强，需要单独的转写模型、延迟、费用与录音告知设计，不以文字提纲功能冒充已实现实时语音面试助手。

## 16. 综合评估与人工决定

### 16.1 报告内容

当前岗位及版本；材料清单与完整度；逐项岗位证据；可以支持的判断；反证或口径冲突；尚无法判断的事项；建议补充的实操/复试问题；替代岗位的岗位相关证据；人工下一步记录。

AI可以写“建议复试核验X”或“目前缺少独立交付证据”，不能替人做最终录用/淘汰。岗位推荐以技能与经历为依据，不用MBTI进行岗位分配。

### 16.2 面试官评价

每个面试官先提交自己的评价，再查看汇总，避免早期意见互相带偏。HR可要求补充证据；评价修改保留版本。系统显示分歧，不把所有人意见简单平均成确定结论。

人工结论状态：继续沟通、补充材料、复试、实操验证、暂缓、当前岗位不推进、拟录用、已接受、入职、候选人退出。需要有负责人、理由、时间和相关材料。

### 16.3 入职与员工档案

录用/入职后关联员工档案，保留招聘历史的访问边界；不是把所有招聘私密笔记默认开放给全体管理者。员工发展测评与招聘材料按各自用途管理。

第一版员工档案含所属部门、岗位、负责人、入职状态、发展记录、测评历史和合适的培训建议；考勤、薪酬、社保、绩效系统对接另立需求。

## 17. AI配置中心

### 17.1 全局供应商与按功能覆盖

用户只需在后台维护供应商与密钥；每个功能可继承默认配置，也可选择不同模型或独立密钥。不要在十个页面各存一份明文Key。

```text
组织全局默认
  → 功能专属供应商/模型/密钥覆盖
     → 被授权的单次运行配置（可选）
```

凭据通过服务端秘密引用使用，不返回浏览器或扩展。API Key不应放在前端、本地公开配置或代码仓库。[R5]

### 17.2 供应商配置字段

供应商名称、协议适配器、API Base URL、Secret引用、模型ID、能力声明（文本/结构化/图像/转写/向量）、服务区域、允许的数据等级、服务商数据处理配置、超时、并发、速率上限、重试、允许备用模型、启停状态、价格版本与币种。

协议可预留OpenAI官方、经验证的OpenAI兼容接口、其他供应商原生协议和获批准的本地模型。不能假定所有“兼容接口”都支持完全相同参数；供应商特有参数由能力适配器校验。

不写死“某某最新模型”，配置真实模型ID并测试能力。切换模型不需要改业务代码，但要验证JSON输出、长度、费用计量与数据允许范围。

### 17.3 功能映射表

| 功能ID | 默认是否需要LLM/服务费用 | 输出 |
|---|---|---|
| job_optimize | 是 | 岗位建议与差异 |
| resume_extract | 复杂语义时用；纯文本层读取可本地完成 | 结构化经历与证据 |
| resume_vision | 仅文本不可用时 | OCR/视觉抽取结果，费用单列 |
| resume_screen | 是 | 岗位证据比较与未知项 |
| assessment_score | 固定规则，不需要LLM | 确定性计分 |
| assessment_narrative | 可选 | 对已计算结果的补充解释 |
| interview_plan | 是 | 面试题与追问依据 |
| interview_followup | 可选 | 基于已记录问答的下一问建议 |
| audio_transcribe | 转写服务或本地计算，计费独立 | 说话人与时间戳文稿 |
| interview_analyze | 是 | 面试证据摘要 |
| talent_review | 是 | 岗位综合证据报告 |
| talent_search | 可纯结构化；语义检索可用向量服务 | 权限内候选人检索结果 |

第三方授权测评引擎即使不用LLM，也可能另有服务费，不能写成所有测评免费。

### 17.4 功能详情页

显示继承关系、所选模型、密钥尾号、提示词版本、允许输入字段、最大输入长度、最大输出长度、超时、重试次数、温度等受支持参数、输出Schema、每日/月预算、人工复核规则、备用策略。

按钮包括测试连接、用虚构样例试跑、预览输出、保存草稿、发布配置、回滚。测试连接不使用真实候选人简历。只保存配置不能自动触发付费测试，需显式点击。

岗位优化、简历筛选、测评解读、面试提纲、面试分析等页面右上角都提供「AI设置」入口，直达该功能的配置页；页面显示当前生效模型、提示词版本及用量。普通操作者仅查看生效配置，具有权限的管理员可在这里覆盖默认配置。各入口写入同一配置中心，不产生多份互相冲突的Key。

### 17.5 费用与预算

每次调用记录：租户、功能、业务对象、模型、供应商请求ID、输入/输出/缓存Token（供应商返回时）、音频时长、费用币种、价格版本、耗时、状态、重试、操作者。

没有真实usage就记“未知/估算”，不能记0。文本估价公式仅为工程计算：

```text
预计文本费 = 输入Token/1,000,000 × 输入单价
           + 输出Token/1,000,000 × 输出单价
           + 其他适用计费项
```

按供应商计费口径处理缓存、推理Token、图片、工具和音频，禁止重复加算已包含的Token。单价不从文稿猜测，由后台填写并标记生效时间。

任务启动先原子预留最大估算预算，结束结算实际额；失败/重试也计入额度。预算接近阈值提醒，耗尽停止启动新的付费任务；已发出的上游请求不保证能取消或退款。禁止备用模型绕过预算或数据区域限制。

### 17.6 AI失败降级

没有Key：基础档案、H5作答、固定计分和人工流程继续可用，AI按钮显示未配置。模型故障：重试后转人工，保留上次报告并标明未更新，不用虚构结果补位。输出被截断、拒绝、Schema不符、证据校验失败分别显示，不能全部误记为请求成功。

## 18. 智能体编排与提示词

采用明确的工作流节点，不让一个无边界智能体同时抓网页、改库、打分、发邀约和决定录用。

通用流程：取授权材料 → 最小必要字段与脱敏 → 调用指定模型 → 验证JSON结构 → 校验证据引用/数值 → 写入草稿 → 人工复核或按已授权低风险规则流转。

结构化输出能约束格式，不保证字段里的事实正确；必须继续验证来源和业务规则。[R6]

各智能体边界：

| 智能体 | 允许输出 | 禁止动作 |
|---|---|---|
| 岗位优化 | 建议稿、缺项、差异 | 擅自发布/承诺薪资福利 |
| 简历解析 | 有来源字段和疑问 | 填造经历、隐藏联系方式、猜人格 |
| 简历比较 | 岗位证据与待核验项 | 自动拒绝、以人格排序 |
| 测评解读 | 引用现有结果的说明 | 更改基础分或补齐未知算法 |
| 面试规划 | 中立问题与证据目标 | 诱导式证伪、追问无关隐私 |
| 面试整理 | 说话人归属和事实摘要 | 把面试官假设当候选人经历 |
| 综合评估 | 支持/冲突/未知与下一步建议 | 自动录用或以MBTI分配岗位 |

完整提示词模板见 `docs/04_AI智能体提示词.md`。提示词必须版本化，变量通过结构化注入；简历和转写内的文本无权修改系统指令、导出数据或执行工具。

## 19. 推荐技术架构

### 19.1 先检查已有工程

Codex先读取现有代码、依赖、数据库和登录方式。有成熟现有工程时优先增量扩展；未经确认不删除目录、不重建生产库、不替换既有用户系统、不自动部署生产。

没有现有工程时，建议采用TypeScript模块化单体：React管理端与独立H5应用、NestJS API与Worker、PostgreSQL、Redis/BullMQ、私有对象存储、统一AI Gateway。任务队列用于批处理、重试和长任务，不把长音频和500份简历放在一个同步HTTP请求里。[R7]

推荐React + Vite + TypeScript，后台组件库统一选一种成熟方案，H5独立轻量组件；避免同时引入多套重型UI库。依赖使用开发时经核验的稳定版本，写入锁文件，不使用不固定的latest镜像标签。

### 19.2 模块与目录

```text
apps/
  admin-web/            电脑管理端
  assessment-h5/        独立移动测评入口
  api/                  认证、业务API、权限和回调
  worker/               解析、AI、转写、计分、导出、保留清理
  recruiter-extension/  可选、仅获许可渠道的辅助扩展
packages/
  contracts/            DTO、Schema、错误码
  domain/               状态机与领域规则
  assessment-engine/    固定计分、版本与追踪
  report-engine/        模板和受众字段隔离
  ai-gateway/           供应商、模型、预算与输出校验
  channel-adapters/     能力声明与授权接口
  security/             访问控制、脱敏、审计
infra/
  compose/ migrations/ deployment/
docs/ tests/
```

第一版避免无必要拆成十几个微服务。后台与H5可以同部署集群但使用独立路由和构建产物；候选人接口不能复用管理员详情接口再靠前端隐藏字段。

### 19.3 数据与文件

结构化业务写PostgreSQL；文件写私有对象存储；队列和短期锁写Redis。向量检索作为可选增强，先做好结构化检索。向量不是匿名数据，采用与原文同等权限、保留和删除机制。

数据库层可使用行级安全强化租户隔离，但应用仍需对象权限；注意数据库所有者、特权角色等绕过路径，运行账户不能拥有不必要权限。[R8]

## 20. 数据模型

### 20.1 公共字段与约束

业务表包含ID、tenant_id、created_at、updated_at、created_by、revision；涉及保留的数据包含purpose_scope、retention_until和处理状态。软删除不等于完成隐私删除，后续有物理清理流水线。

涉及跨表关联，验证同租户/同对象范围，不接受客户端任意tenant_id。使用外键、必要的组合唯一索引及状态转换验证，防止错绑候选人和岗位。

### 20.2 核心表

| 表 | 关键内容 |
|---|---|
| tenants / departments | 组织、部门、数据地域与政策 |
| staff_users / memberships / roles | 身份映射、组织成员与权限 |
| jobs / job_versions | 岗位主档、不可变版本、确认状态 |
| job_criteria | 必要任务、证据标准、核验方式、可选权重 |
| channel_connections | 接入能力、授权凭据引用、有效期 |
| channel_job_postings | 外部岗位ID、原文快照、内部映射与冲突 |

### 20.3 关键关系

`candidate 1:N application`；`application N:1 job`；`job 1:N job_version`；`candidate 1:N resume_version`。每次筛选与面试固定岗位版本和材料版本。

`assessment_assignment`绑定候选人或员工二者之一，招聘用途可关联application；一个邀请只创建一份正式session，重测新建assignment。答题结果独立于岗位，因此同一测评是否用于其他用途必须另作范围检查，不为了新岗位改分。

`report_version`记录生成输入、规则、提示词、模型与受众。面试文稿修订产生新版本并标记关联报告可能过期，旧报告可追溯。

### 20.4 唯一与并发

候选人去重至少约束 `(tenant_id, channel_connection_id, external_candidate_id)`；简历使用来源与内容哈希识别新版本；相同人不同来源只在可靠核验后合并。

岗位申请允许关闭后再次申请，不能用永久唯一 `(candidate_id, job_id)` 把历史覆盖；可采用申请批次ID并限制同一批次的活跃重复。

提交、计分和AI任务用幂等键；数据事务通过outbox投递任务，不能数据库已提交但队列失败就永远不处理。

## 22. 任务、状态机和一致性

筛选任务状态：draft、queued、running、waiting_for_device、waiting_for_authorization、paused、partially_completed、completed、failed、cancelled。每项有独立状态，不能一项失败回滚全部成功数据，也不能“部分完成”显示成全部完成。

候选人主档状态和申请状态分开；数据保留/禁止联系是第三套独立状态。人才储备不等于同意后续无限联系。

异步节点采用有限重试与退避，区分暂时故障、配置错误、权限错误、数据错误。权限错误不循环重试。任务有心跳、锁过期、恢复策略和最大运行时间。

AI调用、结果保存与后续通知分离；以 `tenant + feature + input_hash + job/rubric_version + prompt_version + model_config_version`形成缓存/幂等参考。缓存不能跨租户共享真实候选人内容，也不能在撤回或到期后继续命中。

## 23. 安全、隐私与内容权利

### 23.1 上线前的数据责任

默认按面向中国境内招聘和员工的业务设计，实际部署主体、数据地域、服务商及其他适用规则需在上线前确认。依法确定告知、处理依据、必要范围、期限和个人权利流程；自动化决策、委托处理、敏感信息和跨境处理等适用影响评估要求应单独核查。[R1]

不把一个总勾选框作为所有未来用途的无限同意。当前招聘、长期储备、录音、外部AI处理和可选发展测评分别说明；需单独同意的情形独立处理。拒绝可选MBTI/发展问卷应有替代评估路径，不自动损害招聘机会。

### 23.2 外部模型

候选人材料默认不无差别发送给所有供应商。先进行字段最小化、去标识和区域/用途检查，记录被发送的数据类别；去掉姓名并不自动使数据成为匿名信息。

备用模型必须满足同一授权范围、数据等级和地域要求。不因主模型失败而静默将资料发送海外。涉及独立第三方/境外服务的具体义务上线前核查，系统通过配置拦截不允许的路由。

### 23.3 密钥与网络

密钥以托管秘密服务或信封加密方式存储，解密密钥不与业务库备份放在一起；只显示尾号，支持轮换和撤销。服务端调用；前端、H5、插件、日志、导出和Git不得出现完整密钥。

供应商Base URL仅管理员可配，校验HTTPS、域名、DNS和重定向，限制访问内部元数据地址，防止SSRF。本地模型使用预先批准的服务白名单，不开放任意内网URL代理。

### 23.4 内容与导出

简历/报告HTML严格消毒；文件隔离预览；导出CSV/表格处理公式注入；文件下载短期签名、对象绑定、权限复核；批量导出和联系信息读取留审计。

### 23.5 删除闭环

删除流程覆盖主档、联系方式、原件、提取文本、向量、报告、缓存、搜索索引、消息草稿和委托服务可执行的删除请求。法律要求保留或技术备份暂不可立即删除的部分限制后续使用并记录依据/到期。

备份有期限与删除抑制名单；恢复备份后先重放删除和权限撤销事件，再开放访问，防止已删除人才重新出现。操作审计遵循必要性，不能把被删除简历全文再存进“永久审计”。

### 23.6 原题与报告权利

原题、说明文本、报告模板和品牌元素的使用范围需核验。允许使用的材料按授权条件导入；未确定使用权时可实现同类功能框架与原创界面，不默认复制原站商标、完整商业文案或受限制内容。此处是交付前条件，不以授权问题为由搁置不依赖这些材料的模块。

## 24. 非功能需求与运行

### 24.1 拟定工程目标（非已测成绩）

在明确硬件、数据规模和并发条件后验收：常规列表/详情P95目标不超过1.5秒；H5答案保存P95目标不超过1秒；AI长任务通过异步进度反馈，不承诺固定生成秒数。

以10万份虚构人才档案验证分页/检索，至少100个同时作答会话验证保存与提交幂等。500份/日是业务处理目标，外部获取与模型耗时分别测试，记录真实配额、Token、失败和费用，不以小样本本地演示代替外部稳定性。

### 24.2 环境

开发、测试、生产隔离；生产不默认植入演示账号和示例候选人。环境变量模板无真实密码；管理员初始化通过安全的一次性流程。

提供Docker Compose开发运行方案、数据库迁移、种子数据、健康检查、日志与指标。生产TLS、域名、对象存储权限、秘密服务、备份策略由部署说明列出。

### 24.3 可观测与恢复

监控队列长度、处理延迟、解析失败率、答卷保存失败、重复任务、模型费用、授权失效和设备离线。日志默认不包含简历全文、答题内容、完整手机号、邀请Token或Key。

备份目标与恢复时长由业务确认；交付至少一次测试环境恢复演练及结果，不声称“有备份配置”就是“已验证可恢复”。

## 25. 验收概览

详细用例见 `docs/03_验收与开发阶段.md`。以下为不得缺少的主链路：

A. 新建岗位、优化、人工采纳版本、导入候选人，建立申请；B. 基于授权资料批量初筛，待核验项不被自动淘汰；C. 生成个人H5链接，微信预览不占用，答题弱网可恢复且无错绑；D. 固定计分或外部结果导入，分数与解释状态独立；E. 岗位证据面试题、上传文稿/录音、归属到正确说话人；F. 综合评估、人工作出下一步、未邀约人才按期限留存；G. 每项AI配置可实际生效、用量可追踪；H. 权限、Token、撤回删除和预算测试通过。

未知原站规则应被发布校验拦住，是正确结果；把演示分数显示成真实测评分是失败。未接入平台显示待授权，是正确结果；假数据假装已抓到真实BOSS简历是失败。

## 26. 实施顺序

阶段0：检查仓库与资料；产出范围、证据清单、缺项与数据模型；不连接真实平台、不使用真实候选人做无授权测试。

阶段1：登录与权限、岗位、人才档案、简历导入、岗位申请、来源证据，建立可用电脑后台。

阶段2：独立H5、专属邀请、版本绑定、作答保存/提交、规则包管理和外部报告导入；授权规则未齐时正式计分保持阻塞。

阶段3：AI Gateway、岗位优化、简历结构化、岗位证据初筛、提纲、文稿分析、综合评估、模型费用面板。

阶段4：音频转写、数据保留/删除全链路、受众报告、导出、员工发展档案、批量筛选队列。

阶段5：已获许可渠道适配与同步、允许的浏览器辅助模式、500份任务压力/费用测试；无许可平台只交付接口和人工替代路径。

阶段6：规则包完整后做逐项兼容验证与生产发布；每项缺失条件单列，不阻塞已经可用的招聘功能。

后续增强：完整实时语音追问、更多招聘渠道、经授权组织共享、成熟的团队发展看板。均不包含“自动按人格安排岗位”。

## 27. Codex交付要求

必须交付可运行代码，不只画后台页面。包括：前后端、数据库迁移、固定计分框架、AI适配器、接口契约、权限校验、测试、环境变量模板、运行说明、演示数据、已实现清单、未实现/待授权清单。

先做一条真实可验收链路，再扩展批量与渠道。缺外部Key使用明确标识的mock验证接口，不以mock通过声称真实模型已联调。缺完整题库/公式时不得让LLM现场编题和编分并挂“100%原版”。

每阶段汇报：修改了哪些文件、实际运行哪些命令、哪些测试通过/失败、哪些功能未测、下一阶段依赖。没有运行的测试写“未运行”。

代码规范：类型明确、输入验证、错误分类、中文界面、模块边界、可回滚迁移、最小权限、关键流程幂等。禁止写死候选人评语、模拟真实抓取成功、固定假匹配分、明文Key、公开简历下载路径和仅前端鉴权。

在既有工程中的破坏性修改、生产部署、真实对外发送、付费解锁/购买必须另行确认。正常编码和本地虚构数据测试可按计划推进，不因题库缺项反复阻塞整个系统。

## 28. 最终完成的判定

不是“页面看起来齐全”，而是：一个岗位、一位候选人、一个专属邀请、一份可追溯结果、一场有证据的面试、一项人工决定，能够在同一档案中串起来；未邀约资料能按授权用途留存并再次检索；任何AI结论能定位材料，任何数据访问有范围，任何外部依赖缺失都不会被伪装成已经成功。
